# Пошаговый runbook: AI-разработка с двумя раздельными репозиториями

Версия: 3.1
Дата: 27 августа 2026 г.
Целевая аудитория: AI-интегратор, который впервые подключает AI к проекту.

Эта версия описывает весь жизненный цикл:

1. согласование использования AI;
2. создание и защита приватного AI-репозитория;
3. подключение готового Starter Kit к checkout проекта;
4. установка единой команды `aiw`;
5. подключение Codex Desktop и Claude Desktop без AI-файлов в project repo;
6. настройка Starter Kit агентом;
7. ежедневную работу команды от задачи до human-reviewed PR;
8. onboarding, offboarding, аудит и обновление;
9. controlled learning loop для улучшения skills на реальных ошибках без project artifacts.

Актуальные артефакты:

- каталог `project-ai-workspace-template` — Starter Kit;
- `project-ai-workspace-template/CHANGELOG.md` — изменения и миграция версии 3;
- `project-ai-workspace-template/INCIDENT-RESPONSE-RU.md` — incident response и rollback;
- `project-ai-workspace-template/TASK-CONTEXT-RU.md` — короткий flow передачи разрешённых Jira/Confluence-артефактов без доступа AI к этим системам;
- `project-ai-workspace-template/SETUP-PROJECT-WITH-AGENT-RU.md` — инструкция, по которой агент донастраивает пару репозиториев;
- `project-ai-workspace-template/DESKTOP-AND-CLI-RU.md` — короткая инструкция по CLI и Desktop.

Каталог является единственным source of truth. ZIP не хранится в Git и при необходимости создаётся локально командой `npm run package`.

В этом runbook единственный поддерживаемый путь — готовый Starter Kit с JSON-конфигурацией. Ручные пояснения используются только для аудита и восстановления утверждённого состава, а не как альтернативная схема настройки.

## 1. Что должно получиться в конце

Для каждого проекта существуют ровно два Git-репозитория.

### Репозиторий 1: проектный

Условное имя: `project-repository`.

Содержит:

- продуктовый код;
- тесты;
- продуктовую и эксплуатационную документацию;
- обычные спецификации и ADR, если они приняты процессом проекта.

Не содержит:

- agents, skills и prompts;
- конфигурации конкретного AI-инструмента;
- транскрипты и память агента;
- временные AI-планы;
- внутренние eval-наборы;
- подписи `Generated by AI`, AI co-author trailers и аналогичные служебные следы.

### Репозиторий 2: приватный AI-workspace проекта

Условное имя: `project-ai-workspace`.

Содержит:

- роли агентов;
- skills и инструкции;
- шаблоны specification, plan, tasks, review и documentation;
- project profile;
- workflow для feature, bug fix, tests и docs;
- правила доступа агента;
- launcher для запуска AI-сессии;
- сканер утечки AI-артефактов;
- обезличенные project-specific evals;
- журнал решений по настройке AI-процесса.

Не содержит:

- копию исходного кода проекта;
- secrets;
- production data;
- персональные данные;
- полный transcript работы с кодом проекта;
- credentials для Git, CI/CD, cloud и production.

### Как репозитории связаны

Они не связываются средствами Git. Не используются:

- Git submodule;
- Git subtree;
- вложенный Git-репозиторий;
- символическая ссылка из репозитория проекта;
- копирование AI-файлов в checkout проекта.

Оба репозитория клонируются в соседние локальные каталоги. Launcher из AI-репозитория получает путь к checkout проекта, проверяет его remote URL, запускает агента с каталогом проекта как рабочей областью и подгружает инструкции из AI-репозитория.

Итоговая структура на компьютере разработчика:

```text
workspaces/
└── acme-billing/
    ├── project-repository/               # Git remote проекта
    ├── project-ai-workspace/  # приватный Git remote AI workspace
    ├── .ai-context/                 # временные разрешённые материалы задач; не Git
    └── .ai-runtime/                 # launcher-managed runtime; не Git
```

## 2. Обязательные решения до технической настройки

### Шаг 1. Назначить владельцев

Заполните таблицу и сохраните её во внутренней системе управления проектом.

| Ответственность | ФИО/роль |
|---|---|
| Разрешает использование AI на проекте | Delivery manager |
| Проверяет договор и confidentiality | Legal/Account manager |
| Утверждает AI-инструменты | Security/IT |
| Владеет AI-workspace | AI integrator |
| Утверждает архитектурные изменения | Tech lead/архитектор проекта |
| Принимает код | Human reviewer |
| Реагирует на утечку данных | Security incident owner |

Проверка: у каждой строки есть конкретный человек, а не только название отдела.

Результат: понятно, кто принимает решение, если AI просит доступ, возникает риск или нужен exception.

### Шаг 2. Проверить договорные условия проекта

Вместе с Legal/Account manager ответьте письменно:

1. Разрешено ли применять generative AI при разработке?
2. Нужно ли уведомить владельца проекта или получить согласие?
3. Можно ли передавать исходный код стороннему AI-провайдеру?
4. Разрешены ли subprocessors и в каких странах?
5. Какие требования действуют к retention и удалению данных?
6. Есть ли специальные требования к IP, лицензиям и code provenance?
7. Какие данные запрещено передавать при любых условиях?

Если хотя бы на один критичный вопрос нет ответа, не подключайте AI к коду проекта. Разрешены только публичные или синтетические примеры до получения решения.

Проверка: существует датированное решение `Allowed`, `Allowed with restrictions` или `Not allowed`.

Результат: определена правовая граница использования AI.

### Шаг 3. Выбрать режим данных

Выберите один режим.

| Режим | Что разрешено |
|---|---|
| Green | публичный код, synthetic data, общие технические вопросы |
| Amber | код проекта через утверждённый enterprise/API AI-сервис; без secrets и production data |
| Red | код проекта нельзя отправлять внешней модели; только approved local/on-prem AI либо работа без AI |

Запишите выбранный режим в `project/profile.json`, который будет настроен далее.

Проверка: Security и Delivery manager согласовали режим.

Результат: разработчик понимает, что разрешено передавать агенту.

### Шаг 4. Выбрать AI-инструмент

Проверьте отдельно IDE chat, CLI/local agent, cloud agent, code review и MCP/plugins. Для каждой функции ответьте:

- используется ли input/output для обучения;
- каков retention;
- где обрабатываются данные;
- есть ли SSO/MFA и корпоративное управление;
- можно ли запретить отдельные модели и функции;
- можно ли ограничить filesystem, network и команды;
- доступны ли audit logs;
- можно ли отключить cloud agent и сторонние MCP;
- как выполняется удаление данных.

Настройка для первого пилота:

- используйте корпоративный аккаунт;
- отключите preview-функции;
- отключите cloud agents;
- отключите все MCP/plugins, затем разрешайте по одному;
- разрешите только утверждённые модели;
- включите минимально возможный retention;
- запретите обучение на business data;
- включите public-code matching/blocking, если функция доступна;
- запретите использование personal/free accounts.

Проверка: Security сохранил скриншоты или экспорт настроек и дату проверки.

Результат: определена управляемая поверхность AI, которую можно использовать в пилоте.

## 3. Создание приватного AI-репозитория

Выберите только одну инструкцию: GitHub, GitLab или Bitbucket. Репозиторий проекта и AI-репозиторий могут находиться на разных платформах; локальная связь от этого не меняется.

Используйте имя `<project-name>-ai-workspace`, например `acme-billing-ai-workspace`. Не включайте в имя секретный codename или персональные данные.

### Вариант A. GitHub

#### Создать репозиторий через интерфейс

1. Войдите в корпоративную организацию GitHub.
2. В правом верхнем углу нажмите `+`.
3. Выберите `New repository`.
4. В поле `Owner` выберите корпоративную организацию, не личный аккаунт.
5. В `Repository name` введите `<project-name>-ai-workspace`.
6. В `Description` укажите `Private AI delivery workspace for <project-code>. No project source code.`
7. Выберите видимость `Private`. Не выбирайте `Internal`, потому что internal-репозиторий может быть доступен всем участникам enterprise.
8. Включите `Add a README file`.
9. Выберите корпоративный `.gitignore` для ОС или оставьте без шаблона; полный файл будет добавлен далее.
10. Нажмите `Create repository`.

Официальная последовательность создания: [GitHub Docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository).

#### Настроить доступ

1. Откройте репозиторий.
2. Перейдите `Settings` → `Collaborators and teams` или `Manage access`.
3. Добавьте команду проекта.
4. Разработчикам дайте роль `Write`.
5. AI-интегратору и одному резервному владельцу дайте `Maintain`.
6. Роль `Admin` оставьте только владельцам организации/репозитория.
7. Удалите прямой доступ людей, которым репозиторий не нужен.

Официальная справка по team access: [GitHub Docs](https://docs.github.com/en/enterprise-cloud%40latest/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/managing-team-access-to-an-organization-repository).

#### Защитить main

1. Перейдите `Settings` → `Rules` → `Rulesets`.
2. Создайте branch ruleset для `main`.
3. Запретите force push и deletion.
4. Включите обязательный pull request.
5. Требуйте минимум одного approval.
6. Включите dismiss stale approvals после новых commits.
7. Запретите bypass всем, кроме двух администраторов для аварийного восстановления.
8. Сохраните ruleset и переведите его в `Active`.

Проверка: обычный разработчик не может выполнить прямой push в `main`.

### Вариант B. GitLab

#### Создать project/repository

1. Войдите в корпоративную группу GitLab.
2. Вверху нажмите `Create new` → `New project/repository`.
3. Выберите `Create blank project`.
4. В `Project name` введите `<project-name>-ai-workspace`.
5. Убедитесь, что `Project URL/Namespace` указывает на корпоративную группу.
6. В `Project slug` оставьте безопасное имя без секретов проекта.
7. В `Visibility Level` выберите `Private`.
8. Включите `Initialize repository with a README`.
9. Нажмите `Create project`.

Официальная последовательность: [GitLab Docs](https://docs.gitlab.com/user/project/).

#### Настроить участников

1. Откройте project.
2. Перейдите `Manage` → `Members`.
3. Добавьте проектную группу или конкретных участников.
4. Разработчикам назначьте `Developer`.
5. AI-интегратору назначьте `Maintainer`.
6. `Owner` оставьте владельцам верхнеуровневой группы.
7. Не задавайте access expiration `Never` внешним/временным участникам; укажите дату окончания проекта.

#### Защитить main

1. Перейдите `Settings` → `Repository`.
2. Откройте `Branch rules`.
3. Создайте или откройте правило для `main`.
4. `Allowed to push and merge` установите `No one`.
5. `Allowed to merge` установите `Maintainers` или согласованную группу.
6. Отключите force push.
7. В настройках merge requests потребуйте минимум один approval.

Официальная последовательность protection: [GitLab Docs](https://docs.gitlab.com/user/project/repository/branches/protected/).

Проверка: Developer создаёт branch и merge request, но не может push напрямую в `main`.

### Вариант C. Bitbucket Cloud

#### Создать repository

1. Войдите в корпоративный Bitbucket Workspace.
2. Нажмите `Create` → `Repository`.
3. В `Workspace/Project` выберите корпоративный workspace и проект.
4. В `Repository name` введите `<project-name>-ai-workspace`.
5. Оставьте access `Private`.
6. В `Include a README?` выберите `Yes`.
7. Нажмите `Create`.

Официальная последовательность: [Atlassian Support](https://support.atlassian.com/bitbucket-cloud/docs/create-a-repository/).

#### Настроить доступ

1. Откройте repository.
2. Нажмите `More actions (…)` → `Repository settings`.
3. Откройте `Repository permissions` или `User and group access`.
4. Проектной группе задайте `Write`.
5. AI-интегратору и резервному владельцу задайте `Admin`.
6. Остальным задайте `Read` либо удалите доступ.

Официальная справка: [Atlassian Support](https://support.atlassian.com/bitbucket-cloud/docs/grant-repository-access-to-users-and-groups/).

#### Защитить main

1. Откройте `Repository settings`.
2. В разделе `Workflow` выберите `Branch restrictions`.
3. Нажмите `Add a branch restriction`.
4. В `By name or pattern` укажите `main`.
5. Ограничьте direct write администраторами.
6. Разрешите merge только через pull request согласованной группе.
7. Запретите rewriting history и deletion.
8. Если тариф поддерживает merge checks, потребуйте approval и успешный pipeline.

Официальная справка: [Atlassian Support](https://support.atlassian.com/bitbucket-cloud/docs/use-branch-permissions/).

Проверка для любой платформы:

- репозиторий имеет видимость Private;
- владелец — корпоративная организация/workspace/group;
- доступ имеет только проектная команда;
- main защищён;
- personal fork запрещён политикой или процессом;
- включены MFA/SSO и audit там, где это поддерживает тариф.

## 4. Подготовка структуры AI-репозитория

### Основной путь: развернуть готовый Starter Kit

Подшаги 5A–5H ниже описывают получение и первоначальную настройку AI-workspace. Для нового проекта не создавайте эти файлы вручную. Выполните следующий порядок.

#### Шаг 5A. Получить Starter Kit

Возьмите каталог `project-ai-workspace-template` из утверждённой версии этого репозитория.

Перед копированием:

1. считайте каталог `project-ai-workspace-template/` единственным source of truth;
2. выполните `npm test`, `npm run self-test` и `npm run self-scan`;
3. если для передачи нужен ZIP, перейдите в `project-ai-workspace-template/` и выполните `npm run package`; созданный архив остаётся локальным производным артефактом и не добавляется в Git;
4. убедитесь, что версия Starter Kit утверждена Security/AI integrator;
5. не загружайте template в репозиторий проекта;
6. не используйте общий центральный project-agent repo: у каждого проекта будет собственная приватная копия.

#### Шаг 5B. Заполнить пустой приватный AI-репозиторий

Если AI-repo уже клонирован и содержит только README:

1. если используется локально собранный ZIP, распакуйте его во временный каталог; иначе работайте непосредственно с исходным каталогом Starter Kit;
2. скопируйте содержимое каталога `project-ai-workspace-template`, но не сам внешний каталог, в корень AI-repo;
3. сохраните существующий `.git` AI-repo;
4. если README уже существует, объедините его содержание, а не перезаписывайте без проверки;
5. не копируйте `.DS_Store`, runtime, `.env` и архив внутрь AI-repo.

Ожидаемая рабочая структура:

```text
project-ai-workspace/
├── .dockerignore
├── CHANGELOG.md
├── INCIDENT-RESPONSE-RU.md
├── TASK-CONTEXT-RU.md
├── START-HERE-RU.md
├── DESKTOP-AND-CLI-RU.md
├── SETUP-PROJECT-WITH-AGENT-RU.md
├── README.md
├── package.json
├── project/
│   ├── profile.json
│   ├── permissions.json
│   ├── forbidden-artifacts.json
│   └── skill-improvement-policy.json
├── agents/
├── skills/                         feature, bug-fix, testing, docs, improvement
├── workflows/                      включая continuous-improvement
├── templates/
│   └── ci/                         reviewed CI starting points
├── adapters/
├── evals/                          templates и synthetic behavioral cases
├── bin/
│   ├── aiw
│   ├── aiw.ps1
│   ├── aiw.mjs
│   ├── aiw-global.mjs
│   └── aiw-mcp.mjs
├── docker/
└── scripts/                        package и Docker smoke checks
```

Проверка:

```text
node --version
npm test
node bin/aiw.mjs self-test
node bin/aiw.mjs self-scan
git status --short
```

Требуется Node.js 20 или новее. `npm test`, `self-test` и `self-scan` должны завершиться успешно.

#### Шаг 5C. Клонировать project repo рядом

Итоговые каталоги должны быть соседними:

```text
<project-parent>/
├── project-repository/
├── project-ai-workspace/
├── .ai-context/                 создаётся человеком только при необходимости
└── .ai-runtime/                 создаётся launcher автоматически
```

macOS:

```bash
mkdir -p ~/workspaces/<project>
cd ~/workspaces/<project>
git clone <PROJECT_CLONE_URL> project-repository
git clone <AI_CLONE_URL> project-ai-workspace
chmod +x project-ai-workspace/bin/aiw
```

Windows PowerShell:

```powershell
New-Item -ItemType Directory -Force C:\workspaces\<project>
Set-Location C:\workspaces\<project>
git clone <PROJECT_CLONE_URL> project-repository
git clone <AI_CLONE_URL> project-ai-workspace
```

Если AI-repo уже был заполнен локально, повторно его не клонируйте. Разместите project checkout рядом и проверьте оба remote.

#### Шаг 5D. Настроить `project/profile.json`

Starter Kit использует JSON, а не YAML. Сначала прочитайте `project/README.md`: там описаны назначение, допустимые значения, runtime enforcement и последствия изменения каждого ключа во всех JSON-файлах папки. Затем заполните:

1. `project.id` — безопасный slug без персональных и секретных данных;
2. `project.displayName` — внутреннее отображаемое имя;
3. `targetRepository.localRelativePath` — путь от AI-repo к project repo, обычно `../project-repository`;
4. `targetRepository.runtimeRelativePath` — обычно `../.ai-runtime`;
5. `targetRepository.allowedRemotes` — точные SSH и/или HTTPS URL project origin;
6. `targetRepository.defaultBranch` — `main`, `master`, `develop` или реальная ветка;
7. `dataPolicy.lane` — только согласованное `green`, `amber` или `red`;
8. `ai.defaultTool` — `codex` или `claude`;
9. `ai.codex.model` и `ai.claude.model` — утверждённая модель либо пустая строка для enterprise default;
10. `projectCommands` — семь структурированных записей с `mode`, `command`, `args`, `instructions`, `evidenceRequired`.

Получить project origin:

```text
git -C ../project-repository remote get-url origin
```

Не используйте wildcard в `allowedRemotes`. Для каждой операции выберите `agent`, `manual`, `forbidden` или `unresolved`. Режим `unresolved` разрешён во время анализа, но является blocker для `doctor --require-commands` и для запуска ролей `developer`, `qa`, `reviewer`. Не записывайте shell pipeline строкой: executable и аргументы задаются отдельно.

Если обновляется workspace Starter Kit 1.x, выполните миграцию из `project/README.md`: `profile.schemaVersion` и `permissions.policyVersion` становятся `2`, строковые commands преобразуются в records, а неиспользуемые `cloudAgent` и настраиваемые Docker invariants удаляются. Не меняйте только номер версии без преобразования структуры.

#### Шаг 5E. Проверить permissions и delivery hygiene

Откройте:

- `project/permissions.json`;
- `project/forbidden-artifacts.json`;
- `project/skill-improvement-policy.json`;
- `docs/base-instructions.md`;
- `adapters/claude/settings.json`;
- `adapters/codex/README.md`.

Подтвердите:

- агент пишет только в project working tree и внешний runtime;
- commit, push, merge, deploy, destructive Git и production access запрещены или требуют человека;
- network отключён по умолчанию для generated commands;
- `.git`, CI settings и IDE AI settings не меняются;
- scanner запрещает `AGENTS.md`, `CLAUDE.md`, `.codex`, `.claude`, prompts, transcripts и AI attribution;
- Claude attribution и auto-memory отключены внешним adapter;
- project-specific исключения добавляются только после письменного решения.

JSON проходит строгую проверку: неизвестный ключ или неподдерживаемое значение блокирует launcher. Поддерживаемые permission keys реально влияют на CLI arguments, Docker project mount, injected instructions или delivery scan. При этом JSON всё равно не является OS sandbox: native isolation обеспечивает permission system выбранного CLI, а domain-level Docker egress — корпоративный proxy/firewall.

#### Шаг 5F. Донастроить проект вручную или агентом

Ручной вариант: заполните файлы по шагам 5D–5E, затем выполните проверки ниже.

Агентный вариант:

1. откройте AI-repo в Codex или Claude Code;
2. убедитесь, что project repo находится рядом;
3. передайте агенту файл `SETUP-PROJECT-WITH-AGENT-RU.md`;

для соседнего репозитория проекта. Репозиторий проекта не изменяй.

Для Claude замените `codex` на `claude`. Для обязательного Docker mode замените `native` на `docker` после сборки и login.

Что происходит:

Если global installation запрещена:

- macOS: `./bin/aiw ...` из AI-repo;
- Windows: `.\bin\aiw.ps1 ...` из AI-repo.

## 5. Проверка связи и launcher

### Шаг 6. Проверить launcher `bin/aiw`

Launcher — единственная утверждённая точка запуска AI на проекте. Он уже реализован в Starter Kit для Codex и Claude; на проекте его настраивают и проверяют, а не переписывают.

Фактическая последовательность launcher:

1. Найти корень AI-repo по расположению `bin/aiw`.
2. Прочитать `project/profile.json`.
3. Разрешить `targetRepository.localRelativePath` относительно AI-repo.
4. Получить фактический `git remote get-url origin` checkout проекта.
5. Сравнить URL с `targetRepository.allowedRemotes` точным сравнением после нормализации SSH/HTTPS.
6. Убедиться, что AI-repo не находится внутри project-repo и наоборот.
7. Убедиться, что target совпадает с корнем Git worktree; путь на отдельный monorepo-пакет в версии 3.x не поддерживается.
8. Проверить strict schemas, data policy, default ref и текущий project diff.
9. Если существует `../.ai-context/<task-id>/`, проверить его типы, ссылки, размеры и вероятные text secrets.
10. Создать уникальный session directory в `.ai-runtime` и read-only snapshot task context.
11. Собрать инструкции из `project/`, выбранного `agents/`, `skills/` и `workflows/`.
12. Передать trusted instructions отдельно от task context, который маркируется как untrusted evidence.
13. Запустить tool с project-repo как working directory.
14. Применить filesystem/network/approval restrictions и Docker project mount из `permissions.json`.
15. Передать data policy, human gates, protected paths, deny actions и все project command modes агенту.
16. Выполнять project commands только через `aiw check`, без shell parsing; manual/forbidden/unresolved не запускать.
17. После завершения запустить delivery scan, включая protected paths и новые untracked text files.
18. Показать человеку результаты проверок; не выполнять commit, push, merge или deploy.

Интерфейс launcher должен быть одинаковым независимо от tool adapter:

```bash
./bin/aiw doctor
./bin/aiw start --role analyst --task ACME-1234
./bin/aiw start --role developer --task ACME-1234
./bin/aiw check lint --task ACME-1234
./bin/aiw check testTargeted --target path/to/test --task ACME-1234
./bin/aiw verify --task ACME-1234
./bin/aiw finish --task ACME-1234
./bin/aiw context-clean --task ACME-1234 --approved
```

Что делает каждая команда:

- `doctor`: проверяет Git, tool, profile, remotes, permissions и команды проекта;
- `start`: создаёт session и запускает выбранную роль;
- `check`: исполняет только command entry с `mode: "agent"`; manual возвращает инструкцию, forbidden/unresolved блокируются;
- `evidence`: записывает обезличенный результат ручной проверки;
- `verify --task`: выполняет artifact scan и проверяет полный набор обязательных evidence;
- `finish`: блокируется без успешных evidence, создаёт очищенный session summary и удаляет session runtime/evidence задачи.
- `context-clean`: после явного `--approved` удаляет только исходную `.ai-context/<task-id>`; `finish` не удаляет пользовательские файлы автоматически.

Если AI-инструмент требует положить `AGENTS.md`, `CLAUDE.md`, `.cursor` или другой файл непосредственно в project-repo, выберите один из вариантов:

1. используйте внешний user/workspace config инструмента;
2. смените инструмент;
3. согласуйте такой файл с владельцем project repository как обычный поставляемый артефакт и оформите минимальное точечное исключение.

Предпочтителен вариант 1. Starter Kit не создаёт временные AI-файлы в project repository и не пытается автоматически удалить найденные пользовательские файлы.

Проверка `doctor` должна завершаться ненулевым exit code при:

- неверном remote;
- отсутствии project-repo;
- `mode: "unresolved"` в обязательной command entry;
- неизвестном JSON-ключе, неверной schema version или несуществующем default ref;
- project-repo внутри AI-repo;
- неподдерживаемом tool или неустановленном approved CLI;
- незаполненном data lane.

Результат: связь двух репозиториев выполняется контролируемым локальным процессом.

### Шаг 7. Дополнительно создать multi-root workspace

Если команда использует VS Code-совместимый редактор, сохраните файл `project-repository.code-workspace` только в AI-repo:

```json
{
  "folders": [
    { "name": "AI Workspace", "path": "." },
    { "name": "Project Repository", "path": "../project-repository" }
  ],
  "settings": {
    "files.exclude": {
      "../.ai-runtime": true
    },
    "search.exclude": {
      "../.ai-runtime": true
    }
  }
}
```

Открывайте его из AI-repo:

```bash

```

Multi-root workspace создаёт удобное отображение, но не является security boundary. Launcher и sandbox всё равно обязательны.

Проверка: файл существует только в AI-repo; в `project-repository` не появилось `.code-workspace` или `.vscode`.

Результат: разработчик видит оба каталога, но коммитит их в разные remotes.

## 6. Реализация защиты project repository от AI-файлов

### Шаг 8. Проверить встроенный delivery scanner

Scanner встроен в `bin/aiw.mjs`, получает путь project-repo из profile и проверяет:

1. untracked files;
2. staged files;
3. diff относительно default branch;
4. commit messages локальной ветки относительно default branch;
5. protected paths из `permissions.json`.

Алгоритм:

1. Получить unstaged, staged, branch и untracked paths через Git.
2. Проверить существование/доступность default ref.
3. Сопоставить пути с `denyPaths` и `protectedProjectPaths`; protected paths нельзя разрешить через `allowPaths`.
4. Проверить текстовые diff, commit messages и содержимое новых допустимых текстовых файлов по `denyCommitPatterns`.
5. Прочитать для pattern scan только новые допустимые текстовые файлы до 2 MiB; не читать protected/forbidden paths и блокировать новые untracked symbolic links.
6. Блокировать `.gitmodules`, tracked gitlinks и конфигурацию target на подкаталог Git worktree.
7. Выдать отчёт `PASS` или `BLOCK`.
8. При `BLOCK` завершиться ненулевым exit code. Штатные secret/SAST/SCA/license и package-content checks остаются отдельными project/CI gates.

Не удаляйте найденные файлы автоматически: они могут содержать работу пользователя. Покажите точные пути и инструкцию по исправлению.

Проверка:

1. Создайте в project-repo тестовый `AGENTS.md`.
2. Запустите `./bin/aiw verify` из AI-repo.
3. Ожидайте `BLOCK`.
4. Удалите тестовый файл.
5. Повторите проверку; ожидайте `PASS`.

Результат: случайный AI-артефакт блокирует завершение сессии.

### Шаг 9. Установить локальный pre-push hook

Команда `aiw install-hooks` устанавливает hook в `.git/hooks/pre-push` checkout проекта. Hook не коммитится и вызывает scanner из AI-repo.

Требования:

- хранить в hook абсолютный путь к конкретному AI-repo;
- перед push выполнять `aiw verify` через абсолютный путь к launcher и сверять destination remote с allowlist;
- при `BLOCK` отменять push;
- не модифицировать project-repo;
- уметь обновляться командой `./bin/aiw install-hooks`;
- не перезаписывать чужой hook; при конфликте требуется ручное объединение.

Для командного enforcement владелец project repository выбирает и вручную добавляет reviewed CI-фрагмент из `templates/ci/`. Coding agent не получает разрешение обходить `protectedProjectPaths` ради изменения pipeline.

Ограничение: локальный hook можно удалить или обойти. Для высокой гарантии добавьте внешний required status check, который установлен как GitHub App/GitLab integration/Bitbucket app и нейтрально называется `repository-hygiene`. Он проверяет PR diff без хранения project source. Установка такой интеграции требует разрешения владельца репозитория проекта.

Проверка: тестовый запрещённый файл блокирует push.

Результат: ошибка ловится до отправки ветки в project remote.

### Шаг 10. Проверить отсутствие Git-связи

В project-repo выполните:

```bash
git submodule status
git ls-files | grep -E '(^|/)(AGENTS\.md|CLAUDE\.md|\.claude|\.cursor|\.specify|\.codex)(/|$)' || true
git remote -v
```

Ожидается:

- нет AI-submodule;
- нет AI-файлов;
- remote указывает только на репозиторий проекта.

В AI-repo выполните:

```bash
git remote -v
git ls-files | grep -E '(^|/)(project-repo|source-mirror)(/|$)' || true
```

Ожидается:

- remote указывает только на приватный AI-репозиторий;
- копии кода проекта не отслеживаются.

Результат: два репозитория разделены на уровне Git history и remotes.

## 7. Подключение терминала, Codex Desktop и Claude Desktop

Все три интерфейса используют один источник правил: приватный AI-repo. В project repo не копируются инструкции или tool settings.

```text
                         приватный AI-repo
                   profile + roles + workflows
                              │
                         aiw context/verify
                     ┌────────┼────────┐
                     │        │        │
                 Terminal   Codex    Claude
                  aiw CLI   skill   local MCP
                     │        │        │
                     └────────┼────────┘
                              │
                       project checkout
                    обычный diff без AI-файлов
```

### Шаг 11A. Работа из терминала

Откройте project repo. Переходить в AI-repo для ежедневной работы не нужно:

```text
cd <project-repo>
aiw task ACME-1234
```

Короткая команда использует значения по умолчанию:

- tool — `ai.defaultTool` из profile;
- role — `developer`;
- workflow — `feature`;
- mode — `native`.

Полный вариант:

```text
aiw task ACME-1234 --tool codex --role developer --workflow feature --mode native
```

Поддерживаемые роли: `analyst`, `architect`, `qa`, `developer`, `reviewer`, `technical-writer`.

Поддерживаемые workflows: `feature`, `bug-fix`, `testing`, `documentation`.

Полезные команды:

```text
aiw context ACME-1234 --role analyst --workflow feature
aiw doctor --tool codex --mode native
aiw verify --task ACME-1234
aiw finish ACME-1234
aiw context-clean ACME-1234 --approved
aiw projects
```

`context` печатает собранные внешние инструкции и inventory `.ai-context/<task-id>` без запуска AI tool. Небольшие text-файлы выводятся в отдельной секции untrusted evidence. Это используется Desktop-интеграциями и подходит для диагностики. `verify --task` дополнительно проверяет обязательные evidence; `verify` без task выполняет только delivery scan. `context-clean` удаляет только выбранный исходный task context и требует `--approved`.

В native Codex mode launcher отключает apps и memories, но пользовательские skills, plugins и MCP могут оставаться активными. До пилота проверьте пользовательский контекст; для более строгой изоляции используйте enterprise-managed configuration или Docker/VM.

### Шаг 11B. Подключить Codex Desktop

Один раз для каждого проекта:

```text
cd <project-repo>
aiw desktop-install codex
```

Команда создаёт пользовательский skill в `~/.agents/skills/aiw-<project-id>/`. Skill не попадает в project repo и требует:

Codex поддерживает пользовательские skills из `.agents/skills` и их использование в Codex app/CLI; актуальная структура описана в [официальной документации OpenAI](https://learn.chatgpt.com/docs/build-skills).

1. вызвать `aiw context` до планирования или изменения кода;
2. работать только в зарегистрированном project repo;
3. не создавать AI-файлы в project repo;
4. не выполнять commit/push/merge/deploy;
5. вызвать delivery verification перед завершением; финальную проверку evidence и `finish` человек выполняет с task ID.

Работа команды:

1. открыть project repo как workspace Codex Desktop;
2. создать или открыть feature branch проекта;
3. написать:

```text
Используй $aiw-<project-id> для задачи ACME-1234.
Роль developer, workflow feature. Сначала загрузи project context.
Перед завершением выполни AIW verification.
```

4. проверить предложенный plan;
5. разрешать команды только в рамках проекта;
6. после работы самостоятельно проверить diff;
7. commit/push выполняет человек.

После изменения AI-repo обновите launcher и skill:

```text
git pull --ff-only
npm install -g .
aiw register . --force
aiw desktop-install codex
```

### Шаг 11C. Подключить Claude Desktop

Сгенерируйте project-specific local MCP config:

```text
cd <project-repo>
aiw desktop-config claude
```

Команда печатает JSON с сервером `aiw-<project-id>`. Не заменяйте существующий `mcpServers`: объедините новый элемент с существующими настройками либо установите подготовленное корпоративное Desktop Extension.

Claude Desktop поддерживает локальные MCP servers и приватно распространяемые Desktop Extensions; порядок установки и проверки connector описан в [официальной документации Anthropic](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop).

Локальный AIW MCP предоставляет только:

- `aiw_context` — получить role/workflow/policy и inventory внешнего task context;
- `aiw_task_artifact` — read-only прочитать один validated файл по точному относительному пути из inventory;
- `aiw_check` — выполнить разрешённую configuration-driven проверку и записать evidence при переданном task ID; dependency installation через MCP запрещена;
- `aiw_project_status` — показать paths и краткий Git status;
- `aiw_verify` — выполнить delivery scan; финальная task-evidence проверка выполняется через CLI `aiw verify --task <id>`.

Он не предоставляет произвольный shell, commit/push или доступ ко всему домашнему каталогу.

Пошагово:

1. добавьте сгенерированную конфигурацию после human review;
2. перезапустите Claude Desktop;
3. нажмите `+` возле поля ввода → `Connectors`;
4. убедитесь, что виден `aiw-<project-id>` и пять инструментов;
5. откройте project repo через Claude Code for Desktop или разрешённую workspace-папку;
6. напишите:

```text
Вызови aiw_context для ACME-1234 с role developer и workflow feature. Прочитай необходимые файлы inventory через aiw_task_artifact.
Следуй полученным ограничениям. Перед завершением вызови aiw_verify.
Не выполняй commit, push, merge или deploy.
```

7. подтверждайте только ожидаемые filesystem/tool actions;
8. человек проверяет итоговый diff и выполняет Git delivery.

Обычный Claude chat без разрешённой workspace/Claude Code может получить контекст и проверить status, но не должен считаться средой редактирования project repo.

Для масштабирования на команду AI-integrator может упаковать `aiw-mcp.mjs` как приватный `.mcpb` Desktop Extension. Перед распространением нужны security review, versioning, checksum и enterprise allowlist.

### Шаг 11D. Docker mode

Используйте Docker, если native permission model недостаточен или этого требует Security.

Один раз:

```text
aiw docker-build
aiw docker-login --tool codex
aiw docker-login --tool claude
```

Запуск:

```text
aiw task ACME-1234 --tool codex --role developer --workflow feature --mode docker
```

Project checkout монтируется согласно `docker.projectMount`. Effective filesystem mode остаётся read-only, если read-only задан в `native.filesystemMode` или `docker.projectMount`; роли `developer` и `technical-writer` в этом случае блокируются до запуска контейнера. AI-repo и session instructions всегда read-only, авторизация хранится в отдельном named volume, host home и Docker socket не монтируются. Docker не является domain-level egress allowlist; при необходимости используйте корпоративный proxy/firewall.

Перед пилотом и каждым выпуском Docker-изменений на Docker-capable host выполните `npm run docker-smoke` из AI-repo.

### Шаг 11E. Выбрать интерфейс

| Сценарий | Рекомендуемый интерфейс |
|---|---|
| Повторяемая coding-сессия из terminal | `aiw task` |
| Визуальная работа в Codex Desktop | project-specific Codex skill |
| Визуальная работа в Claude Desktop | Claude Code for Desktop + local AIW MCP |
| Строгая host isolation | `aiw task --mode docker` |
| Диагностика без запуска модели | `aiw context`, `aiw doctor`, `aiw verify` |
| Global install запрещён | `./bin/aiw` или `.\bin\aiw.ps1` |

Независимо от интерфейса остаются обязательными specification/plan, human gates, targeted verification, artifact scan и human review.

## 8. Пошаговое выполнение первой feature

### Шаг 12. Подготовить заявку

В task-системе проекта должен быть ID и исходное описание. Не копируйте confidential ticket целиком в AI-repo. Если у AI нет доступа к Jira/Confluence, человек выгружает минимальный разрешённый snapshot во внешний sibling-каталог `.ai-context/<task-id>`.

Перед началом заполните:

- задача: `ACME-1234`;
- человеческий owner;
- ожидаемый результат;
- out of scope;
- data lane;
- уровень процесса: Fast, Standard или High-risk.

Проверка: owner подтверждает, что задача Ready.

Если нужны внешние материалы, создайте папку и положите туда файлы обычным копированием:

```bash
cd ~/workspaces/acme-billing/project-repository
mkdir -p ../.ai-context/ACME-1234
# Скопируйте в ../.ai-context/ACME-1234 только разрешённые документы и вложения.
aiw context ACME-1234 --role analyst --workflow feature
```

На Windows используйте `New-Item -ItemType Directory -Force ..\.ai-context\ACME-1234`. Отдельные import/init/seal команды не требуются: помещение файла в task context является человеческим подтверждением разрешённой передачи. AIW блокирует symlink/hard link, чувствительные имена, неподдерживаемые типы, вероятные text secrets и превышение лимитов. Полные правила находятся в `TASK-CONTEXT-RU.md`.

### Шаг 13. Проверить окружение

```bash
cd ~/workspaces/acme-billing/project-ai-workspace
git pull --ff-only
aiw doctor
```

Затем обновите project-repo:

```bash
cd ../project-repository
git fetch --all --prune
git checkout main
git pull --ff-only
git status
```

Если есть незакоммиченные пользовательские изменения, не удаляйте их. Создайте отдельный Git worktree или попросите владельца завершить текущую работу.

Результат: обе рабочие копии актуальны, target проверен.

### Шаг 14. Создать feature branch проекта

```bash
cd ~/workspaces/acme-billing/project-repository
git checkout -b feature/ACME-1234-short-description
```

Если процесс проекта задаёт иной шаблон branch name, используйте его.

Проверка:

```bash
git branch --show-current
```

Результат: изменения изолированы от main.

### Шаг 15. Запустить analyst

```bash
cd ../project-repository
aiw task ACME-1234 --role analyst --workflow feature
```

Analyst должен выдать draft по `templates/specification.md`:

- inventory доступных task-context файлов и список непрочитанных материалов;
- problem/outcome;
- scope/out of scope;
- acceptance criteria;
- examples и edge cases;
- non-functional requirements;
- open questions;
- источники каждого факта.

Человек отвечает на вопросы и утверждает specification. До утверждения developer не запускается.

Где хранить specification:

- если проект уже хранит specs в своём repo/tracker — сохранить в принятом проектном месте;
- если spec является только внутренним рабочим материалом — оставить его в утверждённой task/document-системе либо текущей AI-сессии; `.ai-runtime` управляется launcher и не является пользовательским document storage;
- не помещать internal draft в project-repo только ради AI.

Результат: существует утверждённый testable contract поведения.

### Шаг 16. Запустить architect

```bash
aiw task ACME-1234 --role architect --workflow feature
```

Architect должен:

1. найти существующие паттерны;
2. перечислить затрагиваемые компоненты;
3. описать data flow и trust boundaries;
4. предложить минимальное решение и альтернативы;
5. определить migrations, compatibility, observability и rollback;
6. определить test strategy;
7. разбить работу на вертикальные slices по 1–5 файлов.

Tech lead утверждает план. Для auth, payments, PII, public API, database migration и infrastructure обязателен High-risk review.

Результат: developer получает ограниченный план, а не общую просьбу «сделать feature».

### Шаг 17. Запустить QA до реализации

```bash
aiw task ACME-1234 --role qa --workflow feature
```

QA формирует независимый test oracle:

- positive cases;
- negative cases;
- boundaries;
- permissions/security cases;
- regression areas;
- доказательство, что тест способен упасть при дефекте.

Не показывайте QA финальную реализацию до фиксации основных сценариев, если это практически возможно.

Результат: тесты не просто повторяют код, который позже сгенерирует developer.

### Шаг 18. Реализовать первый slice

```bash
aiw task ACME-1234 --role developer --workflow feature
```

Developer-agent обязан:

1. реализовать только первый утверждённый slice;
2. не менять unrelated files;
3. не добавлять dependency без human gate;
4. выполнить formatter/lint/typecheck/targeted test;
5. остановиться при неясном бизнес- или security-решении;
6. показать diff и выполненные проверки.

Человек просматривает diff до следующего slice.

Результат: маленькое проверяемое изменение, которое можно понять без AI.

### Шаг 19. Выполнить verification

Сначала выполните подтверждённые команды через контракт AIW. Для `mode: agent` используйте `aiw check`; для `mode: manual` человек выполняет утверждённую процедуру и записывает санитизированный результат через `aiw evidence`. `forbidden` и `unresolved` не обходятся произвольной командой:

```bash
aiw check format --task ACME-1234
aiw check lint --task ACME-1234
aiw check typecheck --task ACME-1234
aiw check testTargeted --target path/to/test --task ACME-1234
aiw check testFull --task ACME-1234
aiw check build --task ACME-1234
aiw evidence build --task ACME-1234 --status passed --note "Approved manual build passed"
```

Фактически применимые проверки определяются mode каждой записи:

1. format/lint;
2. typecheck;
3. targeted tests;
4. integration/contract tests по затронутому flow;
5. build;
6. SAST/SCA/secret/license scan по правилам проекта;
7. ручная проверка acceptance criteria.

После технических проверок отдельно запустите delivery hygiene:

```bash
aiw verify --task ACME-1234
```

`aiw verify --task` проверяет изменённые/untracked пути, добавленные строки и commit messages на запрещённые AI-артефакты, а также требует успешный evidence для каждой применимой записи с `evidenceRequired: true`. Он не подменяет SAST, SCA, secret или license scanning.

Нельзя писать в PR `all tests passed`, если запускалась только targeted subset. Укажите точные проверки.

Результат: получен проверяемый verification report.

### Шаг 20. Выполнить независимый review

```bash
aiw task ACME-1234 --role reviewer --workflow feature
```

Reviewer сравнивает:

```text
specification ↔ technical plan ↔ actual diff ↔ tests ↔ documentation
```

Проверяет:

- scope creep;
- invented API/config;
- auth/authz и validation;
- error handling и logging;
- race conditions и edge cases;
- излишнюю сложность;
- public-code/license risk;
- соответствие проектным паттернам;
- отсутствие AI-артефактов.

После AI-review обязательный human reviewer читает код. Агент не может утверждать собственный результат.

Результат: замечания исправлены или явно приняты человеком.

### Шаг 21. Завершить AI-сессию

```bash
aiw finish ACME-1234
```

Команда должна:

1. повторно запустить artifact scan;
2. заблокировать завершение при отсутствующем или неуспешном обязательном evidence;
3. зафиксировать количество изменённых путей из `git status` checkout проекта;
4. сохранить в AI-repo session summary без project code/prompts;
5. записать metadata сессии, project ID, время, количество изменённых путей и санитизированную evidence-сводку;
6. записать только безопасную task-context metadata: использован ли context, число файлов, общий размер и digest;
7. удалить session runtime, context snapshots, injected instructions и evidence этой задачи;
8. сохранить исходную `.ai-context/<task-id>` до явной человеческой очистки;
9. оставить commit/push человеку.

Допустимый session summary:

- task ID;
- дата;
- tool, role и workflow конкретной сессии;
- project ID и количество изменённых путей;
- delivery hygiene result;
- только санитизированные поля evidence: check, status, source, recordedAt и note.
- только обезличенные task-context поля: used, fileCount, totalBytes и bundleDigest.

После сохранения утверждённой specification и других официальных результатов удалите временные исходники:

```bash
aiw context-clean ACME-1234 --approved
```

Результат: временный контекст очищен, накоплено безопасное процессное знание.

### Шаг 22. Человек создаёт commit и PR

В project-repo:

```bash
cd ../project-repository
git status
git diff --check
git diff
git add <EXPLICIT_FILE_LIST>
git diff --cached
git commit -m "ACME-1234: <human-written description>"
git push -u origin feature/ACME-1234-short-description
```

Не используйте `git add .` для первой проверки. Добавляйте явный список файлов.

PR содержит:

- цель;
- фактические изменения;
- выполненные проверки;
- риски и rollback;
- ссылку на task/spec/ADR;
- никаких AI-signatures.

Проверка: reviewer проекта видит обычный понятный PR, который соответствует правилам проекта.

Результат: feature доставлена без AI-operational artifacts.

## 9. Настройка процессов для следующих участников

### Шаг 23. Onboarding нового разработчика

Дайте разработчику checklist:

1. Получить доступ к обоим репозиториям независимо.
2. Настроить корпоративный Git identity и MFA/SSO.
3. Установить утверждённый AI tool через корпоративный канал.
4. Клонировать оба репозитория соседними каталогами.
5. Выполнить `npm install -g .` и `aiw register .`.
6. Выполнить `npm test`, `aiw self-test`, `aiw self-scan`, `aiw doctor` и установить local hook через `aiw install-hooks`.
7. При необходимости установить Codex skill и Claude MCP по разделу 7.
8. Пройти упражнение с synthetic task.
9. Продемонстрировать, что test AI artifact блокируется scanner.
10. Подтвердить data policy и incident path.

Проверка: onboarding считается завершённым только после практического упражнения.

### Шаг 24. Offboarding

1. Выполнить `aiw uninstall-hooks --project <project-id>`.
2. Выполнить `aiw desktop-uninstall codex --project <project-id>`.
3. Выполнить `aiw unregister <project-id>`.
4. Удалить человека из private AI-repo.
5. Отозвать AI enterprise seat и active sessions.
6. Отозвать Git/SSH/API tokens.
7. Удалить project-specific credentials с managed device.
8. Проверить private forks и local retention по политике компании.
9. Зафиксировать дату и исполнителя.

Результат: бывший участник не может получить новый доступ к AI-workspace или коду проекта.

### Шаг 25. Еженедельная проверка пилота

AI-интегратор собирает:

- количество завершённых и принятых задач;
- cycle time с учётом review/rework;
- размер PR;
- дефекты и rollback;
- rejected/corrected AI outputs;
- AI cost на принятое изменение;
- policy violations;
- artifact leakage events;
- developer feedback.

Не используйте количество prompts/tokens/lines как показатель продуктивности и не применяйте индивидуальную telemetry для performance rating.

Результат: решение о пользе AI основано на поставленном результате.

### Шаг 26. Ежемесячное обновление AI-repo

1. Проверить версии tool/adapters.
2. Повторно проверить vendor privacy/retention settings.
3. Удалить устаревшие агенты и дублирующиеся инструкции.
4. Обновить project commands при изменении CI.
5. Проверить allow/deny rules.
6. Запустить golden tasks/evals.
7. Просмотреть доступ участников.
8. Проверить отсутствие кода проекта и secrets во всей Git history AI-repo.
9. Создать versioned change через PR.

Результат: AI-workspace развивается контролируемо и не становится свалкой prompts.

## 10. Дообучение project skills на результатах работы

### Что здесь означает «дообучение»

Starter Kit не изменяет веса Codex/Claude и не ведёт скрытую автономную память. Дообучается проектный операционный слой:

- роли агентов;
- skills и conditional references;
- workflow и human gates;
- project profile/glossary;
- output templates;
- adapters, launcher и deterministic checks;
- behavioral evals.

Все изменения хранятся в Git приватного AI-repo, проходят review и могут быть отменены. Project repo остаётся без AI-operational artifacts.

### Шаг 27. Зафиксировать плохой результат

Создавайте improvement record, если агент:

- выбрал неправильный этап/роль;
- придумал отсутствующее требование;
- проигнорировал проектный паттерн;
- выбрал неподходящую test boundary;
- выдал непроверенное утверждение;
- пропустил реальный human gate;
- остановился там, где мог безопасно продолжить;
- повторяет одну и ту же материальную ошибку;
- нарушил repository/data policy либо launcher не применил правило.

Не меняйте skill только потому, что не понравился стиль ответа. Нужен наблюдаемый decision failure, влияние и гипотеза улучшения.

Создайте запись `evals/failures/AIW-<number>.md` по `evals/templates/failure-record.md`. Она должна быть synthetic или достаточно обезличенной. Запрещены project source, ticket copy, raw prompt/transcript, logs с данными проекта, secrets, production/personal data и уникальные project identifiers. Отметьте все четыре privacy checkbox; до запуска improvement человек должен установить `Status: accepted`.

### Шаг 28. Определить правильный слой исправления

| Наблюдаемая причина | Где исправлять |
|---|---|
| неверный path/remote/команда/stack fact | `project/profile.json` или glossary |
| роль выполняет чужую ответственность | `agents/` |
| неверное решение для класса feature/bug/test/docs | соответствующий skill/reference |
| пропущен порядок или gate | `workflows/` |
| системно не хватает поля результата | `templates/` |
| правило не было загружено/применено | adapter/launcher |
| ручная проверка должна быть детерминированной | script/scanner |
| неизвестное product behavior | human decision, не skill |
| разовый tool outage/ошибка выполнения | возможно, AIW менять не нужно |

Не дублируйте одно исправление во всех слоях. Выберите primary cause и минимальную точку изменения.

### Шаг 29. Создать regression eval

По `evals/templates/golden-case.md` создайте behavioral case:

1. минимальный synthetic context;
2. реалистичный request без подсказки правильного ответа;
3. ожидаемые decisions;
4. недопустимые decisions;
5. допустимая вариативность реализации/формулировок;
6. evidence-based score.

Проверьте case на текущей версии AIW. Он должен демонстрировать нужную проблему по правильной причине. Exact wording и заголовки не являются качественной проверкой, если это не machine-readable contract.

### Шаг 30. Запустить improvement session

Из зарегистрированного project или AI-repo:

```text
aiw improve AIW-001 --tool codex
```

Или:

```text
aiw improve AIW-001 --tool claude
```

Команда:

1. проверяет зарегистрированную пару и строгую policy schema;
2. требует заранее подготовленный `evals/failures/AIW-001.md` со всеми privacy checks и human `Status: accepted`;
3. фиксирует status и HEAD project repo;
4. создаёт временные improvement instructions со всеми learning-data restrictions;
5. запускает tool с приватным AI-repo как рабочей областью;
6. загружает `project-skill-improvement` и его references;
7. после работы проверяет, что project status и HEAD не изменились;
8. требует `evals/cases/AIW-001.md` и валидирует `evals/results/AIW-001.json` (before/after, adjacent cases, archetypes, pending human review);
9. проверяет, что каждый элемент `adjacentCases` ссылается на существующий файл в `evals/cases/`;
10. запускает structural skill validation и `self-scan` AI workspace;
11. удаляет runtime и показывает AI-repo diff;
12. не выполняет commit/push.

Improvement session поддерживает native mode. Если выбранный security regime разрешает только Docker/VM, не используйте команду до появления утверждённого изолированного improvement adapter; проведите изменение вручную в разрешённой среде.

### Шаг 31. Проверить изменение

Обязательны:

1. failing case теперь проходит по причине, указанной в hypothesis;
2. соседние golden cases не ухудшились;
3. универсальный skill проверен минимум на разных применимых archetypes, например backend и mobile либо frontend и data;
4. skill правильно выбирается и не перехватывает соседние task classes;
5. агент сохраняет автономию в stack-specific технике;
6. не добавились лишние вопросы/refusals;
7. scope, human gates и data policy не ослаблены;
8. `aiw self-test` и `aiw self-scan` проходят;
9. для сложного/high-risk изменения выполнен независимый forward test и human review.

### Шаг 32. Выпустить и распространить улучшение

1. Покажите reviewer failure classification, hypothesis, AIW diff и before/after/adjacent evals.
2. Создайте commit/PR только в приватном AI-repo.
3. Не включайте raw project evidence.
4. Запишите rollback commit/version.
5. После merge команда выполняет:

```text
git pull --ff-only
npm install -g .
aiw register . --force
aiw desktop-install codex       # если изменился установленный Codex skill/launcher
```

Claude local MCP указывает на AI-repo path и получает обновлённый launcher после `git pull`; при packaged `.mcpb` нужно выпустить и установить новую проверенную версию extension.

6. Наблюдайте следующие применения. Если исходная ошибка сохраняется или соседние задачи ухудшились, refine/revert вместо добавления ещё одного конфликтующего правила.

### Governance learning loop

Для каждого проекта назначьте:

- владельца failure triage;
- человека, разрешающего обезличивание реального инцидента;
- reviewer skills/workflows;
- владельца eval baseline;
- release/rollback owner AI-repo.

На ежемесячном review удаляйте дублирующиеся/устаревшие инструкции, а не только добавляйте новые. Оценивайте принятие результата, rework, escaped defects, policy violations и качество решений; не оптимизируйте prompts/tokens/lines of code.

## 11. Критерии готовности интеграции

Интеграция считается завершённой только если выполнены все пункты:

- [ ] договорное решение задокументировано;
- [ ] data lane выбран;
- [ ] approved AI tool настроен корпоративно;
- [ ] private AI-repo создан и защищён;
- [ ] доступ имеет только проектная команда;
- [ ] project-repo и AI-repo клонируются соседними каталогами;
- [ ] profile содержит точный project remote;
- [ ] launcher отклоняет неверный remote;
- [ ] permissions реально применяются adapter/sandbox, а не только записаны в JSON;
- [ ] проект зарегистрирован в локальном AIW registry;
- [ ] `aiw` определяется из project repo;
- [ ] выбранные Desktop-интеграции проверены;
- [ ] agent roles и workflows заполнены;
- [ ] artifact scanner ловит тестовый запрещённый файл;
- [ ] pre-push hook установлен и проверен;
- [ ] project-repo не содержит AI-config, submodule или ссылок на private AI-repo;
- [ ] AI-repo не содержит копии кода проекта;
- [ ] `aiw self-scan` проходит;
- [ ] первая synthetic feature прошла полный flow;
- [ ] первая реальная feature принята human reviewer;
- [ ] runtime cleanup проверен;
- [ ] incident и offboarding процедуры назначены;
- [ ] baseline metrics собраны.
- [ ] определён владелец skill feedback/eval/release loop;
- [ ] команда знает, что learning records не содержат project artifacts;
- [ ] `project-skill-improvement` и шаблоны evals проверены;

## 12. Порядок выполнения без объяснений

Для использования как короткого operational checklist:

1. Назначить ответственных.

## 13. Статус reference Starter Kit и проектные переменные

Reference Starter Kit уже содержит исполняемые launcher, registry wrapper, scanner, hook installer, Codex skill installer, Claude local MCP server, Docker adapter, роли, skills и workflows.

Для каждого нового проекта не переписывайте launcher. Настройте только проектные переменные:

1. project ID и безопасное display name;
2. относительный путь и точные remotes project repo;
3. default branch;
4. согласованный data lane;
5. default tool и утверждённые модели;
6. native или Docker mode;
7. stack-specific install/format/lint/typecheck/test/build commands;
8. project-specific risks, glossary, roles и workflow additions;
9. необходимость Codex Desktop, Claude Desktop и external required status check.

Reference-конфигурация поддерживает Codex и Claude Code, GitHub/GitLab/Bitbucket, native и Docker modes. macOS покрыта исполняемыми тестами; Windows имеет PowerShell launcher, но требует проверки на реальной Windows-машине перед rollout. Project Git platform не влияет на локальную связь: launcher проверяет фактический Git remote.

Для ручной настройки используйте разделы 4–7. Для настройки агентом передайте ему `project-ai-workspace-template/SETUP-PROJECT-WITH-AGENT-RU.md`. После настройки AI-integrator обязан просмотреть AI-repo diff и результаты отрицательного scanner test до merge первой версии AI-repo.
